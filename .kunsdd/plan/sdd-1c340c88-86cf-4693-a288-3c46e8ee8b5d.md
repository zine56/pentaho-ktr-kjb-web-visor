# Pentaho KTR/KJB Web Visor — Implementation Plan

## Summary

Build a **Vue 3 + Vite + TypeScript** single-page web app that opens a local
Pentaho Data Integration (Kettle) file — a `.ktr` transformation or a `.kjb`
job (the draft writes "tr file", a typo for `.ktr`) — parses its XML, and draws
the flow as an interactive graph whose step/job-entry nodes use the **same icons
Pentaho Spoon uses**. The app is **read-only**: "navigate and see", not edit. It
replaces the heavyweight Spoon desktop client for the single job of *viewing* a
flow, which is the pain point in the draft.

The workspace is greenfield (only `.kunsdd` exists), so this plan scaffolds the
app from scratch.

## Goals & Scope (MoSCoW for the first release)

### Must
- Open a local `.ktr` or `.kjb` file via a file picker **and** drag-and-drop.
- Parse the Kettle XML and extract every step (`.ktr`) / job entry (`.kjb`) and
  every hop (connection).
- Render each node with its **name** and a **type-specific Pentaho icon**.
- Render hops as edges between nodes.
- Pan / zoom / scroll the canvas to navigate large flows.
- Show a clear, non-crashing error for malformed or non-Pentaho files.

### Should
- Preserve Spoon's original node positions (`<GUI><xloc>/<yloc>`) when present.
- Auto-layout fallback (Dagre) when positions are missing.
- Visually distinguish disabled hops.
- Show a generic fallback icon for unknown step types (never a blank node).

### Could
- Search / filter by node name or type.
- Minimap and zoom controls (built into the graph library).
- Click a node to inspect its raw configuration in a side panel.
- Export the rendered graph as PNG/SVG.

### Won't (explicitly deferred)
- Editing or saving `.ktr`/`.kjb` files.
- Running transformations/jobs or connecting to databases/repositories.
- Authentication, server-side storage, or multi-user collaboration.
- Handling encrypted/obfuscated Kettle files (out of scope for v1).

## Architecture & Data Flow

Purely client-side; no backend. Domain logic lives outside Vue components.

```
File (drop or picker)
  → File.text()                      (read raw XML as string)
  → parseKettleFile(xml, filename)   (src/parser, DOMParser)
  → KettleGraph model                (src/model: kind, name, nodes[], edges[])
  → toVueFlow(graph) mapper          (src/graph/mapper)
  → Vue Flow nodes + edges           (StepNode custom node renders icon + label)
```

### Domain model (`src/model/graph.ts`)

```ts
export type KettleKind = 'transformation' | 'job';

export interface KettleNode {
  id: string;            // unique; derived from name, disambiguated on duplicates
  name: string;
  type: string;          // e.g. 'TableInput', 'SPECIAL', 'TRANS'
  kind: 'step' | 'entry';
  x?: number;            // from <GUI><xloc>
  y?: number;            // from <GUI><yloc>
  draw?: boolean;        // from <GUI><draw>, defaults true
}

export interface KettleEdge {
  id: string;
  from: string;          // node id
  to: string;            // node id
  enabled: boolean;
  evaluation?: boolean;  // job hops only
  unconditional?: boolean; // job hops only
}

export interface KettleGraph {
  kind: KettleKind;
  name: string;
  nodes: KettleNode[];
  edges: KettleEdge[];
}
```

### Parser behavior (`src/parser/parseKettleXml.ts`)

- Detect kind by root element: `<transformation>` → `.ktr`, `<job>` → `.kjb`;
  also accept the file extension as a secondary hint. Reject anything else with a
  descriptive `KettleParseError`.
- **Transformation**: read `<step>` elements; each has `<name>`, `<type>`,
  `<GUI><xloc>`, `<GUI><yloc>`, `<GUI><draw>`. Read `<hop>` elements with
  `<from>`, `<to>`, `<enabled>`.
- **Job**: read `<entries><entry>` (same `<name>/<type>/<GUI>` shape) and
  `<hops><hop>` (`<from>/<to>/<enabled>/<evaluation>/<unconditional>`).
- Tolerate XML namespaces (parse by `getElementsByTagName` which ignores
  namespace prefixes) and absent `<GUI>` (leave `x/y` undefined).
- Disambiguate duplicate step/entry names by appending ` (2)`, ` (3)`, … and map
  hop `from`/`to` references by occurrence order so edges still resolve.

### Graph rendering (`src/graph/`)

- Use **Vue Flow** (`@vue-flow/core`) with a custom `StepNode.vue` node that
  renders `<img>` (Pentaho icon) + node name. Vue Flow provides pan/zoom,
  minimap (`@vue-flow/minimap`) and controls (`@vue-flow/controls`) out of the box.
- `toVueFlow(graph)` maps `KettleNode` → Vue Flow node (with `position` from
  `x/y`, or a Dagre-computed position) and `KettleEdge` → Vue Flow edge
  (`animated: false`; dashed/red style when `enabled === false`).
- Position strategy: if every node has `x/y`, use them verbatim (mirroring
  Spoon). Otherwise run **`@dagrejs/dagre`** over the whole graph.

## Implementation Steps (ordered by value-per-effort, ICE)

> No `### R-N` requirement blocks exist in the draft, so no `covers:` tags are
> required. Steps are ordered by impact-first, not ease-first.

1. **Scaffold the app.** `npm create vite@latest . -- --template vue-ts`; add
   `@vue-flow/core`, `@vue-flow/minimap`, `@vue-flow/controls`, `@dagrejs/dagre`,
   and `vitest` + `@vue/test-utils`. Commit a blank `App.vue` + a working build.
   *(scaffolding)*

2. **Define the domain model + parser.** Implement `src/model/graph.ts` and
   `src/parser/parseKettleXml.ts` per the spec above, including `KettleParseError`
   and duplicate-name disambiguation. This is the highest-value, highest-risk
   core; do it before any UI. *(ICE: Impact 10, Confidence 8, Ease 6)*

3. **Bundle Pentaho icons + type→icon manifest.** See "Icon Strategy" below.
   Ship `src/icons/stepIcons.ts` (`stepType → asset path`) plus a
   `fallback` icon. *(ICE: Impact 10, Confidence 7, Ease 7)*

4. **Render nodes with icons.** Implement `toVueFlow` mapper and `StepNode.vue`;
   render all nodes with names + icons on a Vue Flow canvas. This is the
   "drawing it" acceptance criterion. *(ICE: Impact 10, Confidence 8, Ease 7)*

5. **Render hops as edges.** Map `KettleEdge` → Vue Flow edges; style disabled
   hops distinctly. *(ICE: Impact 8, Confidence 9, Ease 8)*

6. **Layout: preserve positions, fall back to Dagre.** Use `x/y` when present,
   otherwise auto-layout. *(ICE: Impact 7, Confidence 8, Ease 6)*

7. **File input UX.** File picker + drag-drop drop-zone, error banner for
   `KettleParseError`, empty-state prompt. Wire `File.text()` → parser → graph.
   *(ICE: Impact 8, Confidence 9, Ease 8)*

8. **Tests.** Add Vitest unit tests for the parser (fixtures for `.ktr` and
   `.kjb`), icon mapper fallback, and the mapper. Add one component test that
   `StepNode` renders an `<img>`. *(scaffolding/tests)*

9. **Polish (Could items).** Minimap + zoom controls, click-to-inspect side
   panel, search/filter. Ship only if time allows after Must/Should pass.

## Icon Strategy (Pentaho icons)

The acceptance criterion requires "the same icons that Pentaho uses". Pentaho
Kettle is **Apache-2.0**, including its UI images, so bundling them with
attribution is permitted.

- **Source of truth:** the `pentaho-kettle` GitHub repository. Each step/entry
  plugin declares its icon via an annotation, e.g.
  `@Step(id = "TableInput", image = "TIN.svg", name = "Table input", …)` and
  `@JobEntry(id = "TRANS", image = "TRN.svg", …)`. The image files live in the
  `ui` module (`ui/src/main/resources/ui/images/*`) and per-plugin resources.
- **Build the manifest** by scanning those annotations to produce
  `stepIcons.ts` (id → file). For v1, curate the ~40 most common steps/entries
  and cover the rest with the generic fallback; expand the manifest as a
  follow-up. Do **not** hand-guess filenames — derive them from the annotations.
- Bundle icons as **PNG** (Spoon's native look) at 16px and 32px; include
  Apache-2.0 attribution in a `NOTICE`/README.
- **Fallback:** unknown `type` → a neutral "generic step" icon, so a node is
  never blank.

## Tests & Acceptance Criteria

### Unit tests (Vitest)
- `parseKettleXml`: a `.ktr` fixture yields correct kind, nodes, types,
  positions, and hops.
- `parseKettleXml`: a `.kjb` fixture yields entries and job hops (with
  `evaluation`/`unconditional`).
- Missing `<GUI>` → `x/y` undefined; graph still parses.
- Duplicate step names → unique ids; hops still resolve.
- Disabled hop (`<enabled>N`) → `enabled: false`.
- Malformed XML / unknown root → throws `KettleParseError`.
- `resolveIcon('TableInput')` returns the mapped icon; `resolveIcon('Unknown')`
  returns the fallback.
- `toVueFlow`: node positions preserved when present; Dagre used when not.

### Component test
- `StepNode` renders the icon `<img>` and the node name.

### Acceptance criteria (traceable to the draft)
- **AC1** Load a `.ktr` or `.kjb` via picker and drag-drop. → Steps 1, 7.
- **AC2** All steps/entries drawn as named nodes with Pentaho icons. → Steps 2, 3, 4.
- **AC3** Hops drawn as edges; disabled hops visually distinct. → Steps 2, 5.
- **AC4** Original Spoon layout preserved when present; auto-layout otherwise. → Step 6.
- **AC5** Pan/zoom navigation. → Steps 1, 4, 9.
- **AC6** Unknown types render with a fallback (no blank nodes). → Steps 3, 4.
- **AC7** Clear error for malformed/non-Pentaho files. → Steps 2, 7.

### Manual verification
- Export a real transformation and job from Spoon, load each in the app, and
  compare the rendered graph (node set, connections, positions, icons) to Spoon
  side by side.

## Pre-mortem

If this shipped and failed, the causes would be:

### Tigers — real problems, act on them
| Risk | Class | Mitigation / owner / decision date |
|------|-------|-----------------------------------|
| **Icon fidelity** — wrong or missing step icons breaks the headline criterion ("same icons that Pentaho uses"). | **Launch-Blocking** | Source icons from the Apache-2.0 `pentaho-kettle` repo and derive the id→image manifest from `@Step`/`@JobEntry` annotations (never guess). Add a fallback and verify against a real Spoon export. **Owner:** frontend engineer. **Decision date:** before first release. |
| **Parser gaps across Kettle versions** — XML shape varies (namespaces, older/newer versions), so "loads a file" silently breaks. | **Launch-Blocking** | Parse namespace-agnostically, tolerate absent `<GUI>`, disambiguate duplicate names, and test against fixtures from ≥2 Kettle versions. Scope v1 to non-encrypted files and document the limitation. **Owner:** parser/engineer. **Decision date:** milestone 1. |
| **Layout unreadable for large flows** — stored positions stale or missing, graph becomes a hairball. | **Fast-Follow** | Preserve `x/y` when present; add Dagre fallback; ship minimap + zoom. **Owner:** frontend. **Decision date:** within 30 days. |
| **Performance on very large files** (hundreds of steps). | **Track** | Measure node/edge count; virtualize or cap animations if needed. Monitor, no fix unless it hurts. |

### Paper Tigers — others worry, we do not; document to align
- **"Pentaho icons are proprietary/illegal."** They are Apache-2.0. Include
  attribution; document in README/NOTICE.
- **"We need a server/backend for this."** No — everything is client-side
  parsing + rendering. State this in the plan to prevent scope creep.

### Elephants — unspoken, investigate before committing
- **Does the user want to *edit* files, not just view?** The draft says
  "navigate and see", so v1 is read-only, but if editing is later expected the
  whole persistence model changes. **Investigate** before the first release;
  document the read-only boundary prominently.

## Risks & Deferred Work

- **Encrypted/obfuscated Kettle files** are explicitly out of scope for v1 and
  must produce a clear "unsupported" message rather than a silent failure.
- **Edit/save/run** capabilities are deferred (the draft is view-only).
- **Full 300+ step icon coverage** is deferred; ship curated set + fallback,
  expand the manifest incrementally.
- **Bend points on hops** (curved Spoon hops) are deferred; v1 draws straight
  edges. Positions of the hop routing are not critical to "navigate and see".
